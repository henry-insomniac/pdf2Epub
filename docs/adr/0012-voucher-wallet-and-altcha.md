# 使用额度码钱包与 ALTCHA 降低个人运营门槛

## 状态

已接受。本文扩展 ADR 0011：Stripe Checkout 与 Cloudflare Turnstile 继续保留为可选 provider，但不再是公开模式的强制依赖。

## 决策

公开模式增加 `voucher` 支付 provider 和 `altcha` 挑战 provider。个人运营默认使用这两个 provider：运营者通过只在服务端保存的 HMAC 密钥离线生成固定额度码，在任意合法销售渠道完成收款后交付；用户首次输入时把额度原子写入当前访客钱包。

每个额度码只能入账一次。第一次入账同时永久记录“额度码 ID → 钱包 subject”的关系；之后在其他浏览器输入同一码时，不再次增加额度，而是签发该钱包的新访客会话。因此额度码既是购买凭证，也是 bearer wallet recovery credential。额度码包含到期时间；密钥轮换或码到期后不能再用于恢复，运营者必须备份 HMAC 密钥并建立人工恢复流程。

ALTCHA 由 Go 服务签发两分钟有效的 `PBKDF2/SHA-256` 工作量证明挑战，并使用独立域分离密钥验签。验证成功的 payload 哈希在内存中记录到挑战到期，拒绝重放。它替代外部验证码账号，但不替代边缘限流、源站防火墙、有限队列、额度扣费和资源限制。

## 原因

个人申请跨境支付和验证码服务存在地区、主体审核与结算门槛。额度码把“收款渠道”与“转换额度账本”解耦，允许先通过现有合规渠道人工或半自动交付；ALTCHA 不需要第三方账号和站点密钥。保留 provider 接口可以在交易量足够时切换回自动支付，而无需改动任务 owner、扣费和退款语义。

## 代价与限制

- 当前没有自动订单、自动发码、退款或对账后台；额度码销售和交付由运营者承担。
- 额度码泄露等同钱包被接管，服务端不能区分原持有人与后来持有人。
- 工作量证明会消耗客户端少量 CPU，对低性能设备可能比托管验证码慢；攻击者仍可购买或租用算力。
- 前端 ALTCHA widget 暂从固定版本 CDN 加载，减少构建链；生产 CSP 仅允许该 CDN。后续可把脚本纳入镜像以去除供应链和可用性依赖。
- bbolt 仍限制为单实例账本；横向扩容前迁移 PostgreSQL 和共享 replay store。
